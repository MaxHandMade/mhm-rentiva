# User-account write sites in src/ -- checked by bin/audit-user-account-writes.php.
#
# One line per call site. The text after "--" is for humans: say WHY this surface
# may write a user account and WHICH per-target check stands beside the write.
# The script does not read the justification; the next person to touch this file
# does. It only enforces that the SET of write sites is exactly this set, so a new
# write cannot appear without somebody having to write a line here.
#
# Every claim below was read against the code on 2026-08-17 (6.0.7, WordPress.org
# T9 round). Two shapes recur and they are not the same thing:
#
#   CREATE -- the account does not exist yet, so there is no target for a
#             per-object check to be about. The gate is create_users, which is the
#             capability WordPress itself requires to make a user, plus a nonce.
#   WRITE  -- the target comes from somewhere, so the per-target question has to be
#             asked at the write: current_user_can( 'edit_user'/'delete_user', $id )
#             AND CustomerIdentity::is_customer( $id ). The blanket edit_users says
#             the caller may edit users, not WHICH user. That gap is what T8 found
#             on /customers/bulk and what T9 found in CustomersOptimizer.

src/Admin/Booking/Meta/BookingPortalMetaBox.php | BookingPortalMetaBox::ajax_create_customer_account | wp_create_user  -- CREATE. An operator links a portal account to a booking that was taken off-line (phone, walk-in) so the customer can see it. current_user_can( 'create_users' ) is the handler's first statement, then nonce mhmrentiva_create_customer_account, then current_user_can( 'edit_post', $booking_id ) for the booking being linked. An existing account with that e-mail is linked instead of created.

Nonce first, then current_user_can( 'manage_options' ) for the booking itself, then a SECOND current_user_can( 'create_users' ) for this branch alone -- an operator who may create bookings but not users is told to pick an existing customer. Mandatory here: the booking's meta reads $customer->ID and there is no fallback.
